## Story

**As** the owner of the tool,
**I want** to submit `.docx` files — via upload **or** local path — through the same `/extract` flow I use for PDFs,
**so that** Word documents I receive (briefings, drafts, internal memos) land in the output directory as faithful `.md` files without a manual conversion detour.

## Story Context

**Existing System Integration:**

- Integrates with: `backend/docling_service.py::extract`, `backend/main.py::/extract` endpoint, `frontend/templates/index.html` dropzone, `backend/file_writer.py` filename slug.
- Technology: FastAPI + Docling `DocumentConverter` (already handles DOCX via Docling's native Word backend — no new pipeline), Python-multipart for upload, HTMX for the UI roundtrip.
- Follows pattern: the existing PDF-upload + `local_path` fallback pair (Story 1.4 AC1, Story 1.5 AC2c, Story 1.2 AC1). DOCX plugs into the same dispatch inside `extract()` and the same `/extract` endpoint — no new route, no new response shape.
- Touch points: `extract()` input-type detection, `SourceKind` literal in `backend/models.py`, upload/local-path branches in `main.py::extract_endpoint`, `_validate_local_path` extension-check, `_NamedBytesIO` magic-byte guard, dropzone `accept` attribute, `path-input` placeholder, file-writer slug extension handling, README format-support table.

**Scope decisions locked before draft (PM session 2026-04-24):**

1. **Format scope:** `.docx` only. Legacy `.doc`, `.odt`, `.rtf` are out — will be a separate story if ever needed.
2. **Input modalities:** upload + `local_path` fallback. No remote `.docx` URLs (rare in real workflows; avoids MIME sniffing + HEAD fork for a marginal gain).
3. **Metadata:** extract DOCX core properties (title, author, created-year) and feed the existing conditional-emission rule (PRD FR4 — emit only if confidently detected; omit if absent).
4. **Upload cap:** reuse `MAX_UPLOAD_MB` (50 MB default). No DOCX-specific knob.
5. **Epic placement:** single brownfield story appended to Epic 1 (same precedent as Story 1.7 "post-v1 bugfix / out-of-PRD"). No new epic, no PRD v1.4 amendment — PRD v1.3 remains the v1 MVP snapshot; this story extends FR1 in the brownfield story record itself.

## Acceptance Criteria

1. **AC1 — SourceKind expansion.** `backend/models.py::SourceKind` DEVE ganhar os literais `"docx_upload"` e `"docx_local_path"`, mantendo os quatro existentes. Nenhum outro campo de `ExtractionResult`, `SourceDescriptor`, `ExtractedMetadata` ou `SaveResult` precisa mudar: DOCX reusa a mesma forma de resposta (inclusive `partial`/`failed_pages`/`total_pages`, que permanecem `False`/`()`/`None` para DOCX porque não há chunking nem OCR).
2. **AC2 — Dispatch em `extract()`.** `backend/docling_service.py::extract` DEVE aceitar, em adição aos tipos atuais:
   (a) file-like object (`hasattr(source, "read")`) cujo `.name` termina em `.docx` **ou** cujos bytes começam pelos magic bytes ZIP (`PK\x03\x04`) E **não** começam por `%PDF-`;
   (b) `str` / `Path` apontando para um arquivo `.docx` existente e legível.
   Ambos os caminhos constroem um `DocumentStream(name=..., stream=io.BytesIO(data))` e invocam `_run_docling` single-call (sem chunker — DOCX não tem o problema de pypdfium2 heap; ignore Story 1.7 plumbing). Retornam `ExtractionResult` com `partial=False`, `failed_pages=()`, `total_pages=None`, `source.kind="docx_upload"` ou `"docx_local_path"` conforme origem.
3. **AC3 — Validação de magic bytes DOCX.** A detecção DEVE recusar, com `InvalidInputError` e mensagem acionável, arquivos que:
   (a) têm extensão `.docx` mas **não** começam por `PK\x03\x04` (ex: um `.pdf` renomeado, um `.zip` arbitrário) — mensagem: `"Uploaded/local file is not a valid .docx (missing ZIP magic bytes)"`;
   (b) são ZIP válidos mas não são OOXML Word (ex: `.xlsx`, `.pptx`) — essa detecção pode ser deixada por conta do próprio Docling (`ConversionError` surge naturalmente); não precisamos sniffing profundo do `[Content_Types].xml` para essa primeira iteração.
   Nota: o PDF magic-byte guard existente (`PDF_MAGIC` em `docling_service.py` e `main.py`) permanece inalterado para o caminho PDF — DOCX usa uma constante irmã nova (ex: `DOCX_MAGIC = b"PK\x03\x04"`) exportada do módulo.
4. **AC4 — Endpoint `/extract`: upload + `local_path` aceitam `.docx`.**
   (a) O form field `file` (já multipart) aceita tanto PDF quanto DOCX; a detecção de tipo acontece dentro de `extract()` — o endpoint não roteia por MIME.
   (b) `_validate_local_path` DEVE aceitar extensões `.pdf` **e** `.docx` (case-insensitive). A mensagem de erro para extensões inválidas passa de `"local_path must point to a .pdf file"` para `"local_path must point to a .pdf or .docx file"`. A checagem de magic bytes ramifica por sufixo: `.pdf` → `%PDF-`; `.docx` → `PK\x03\x04`.
   (c) O cap `MAX_UPLOAD_MB` (50 MB) aplica-se identicamente a DOCX: upload `413` antes da conversão; local path `413` via `stat().st_size`.
   (d) O campo `url` continua aceitando **apenas** URLs HTML e PDF. DOCX via URL está fora do escopo desta story — se fornecida uma URL que resolve para `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, o comportamento atual (falha em `_detect_url_kind` → `InvalidInputError "Could not determine content type"`) é aceitável; não precisa de mensagem custom nesta iteração.
5. **AC5 — Metadados DOCX → frontmatter.** Quando disponíveis nas core properties do `.docx` (via `docx.core.xml` do próprio DocumentConverter/Docling **ou** via leitura direta de `docProps/core.xml` se necessário), os seguintes mapeamentos DEVEM ser aplicados, respeitando a regra de omissão de PRD FR4:
   - `dc:title` → `source_title` (string, trimmed)
   - `dc:creator` → `author` (primeiro autor quando houver vários separados por `;`)
   - `dcterms:created` → `year` (int do ano da ISO-8601 quando parseável)
   Campos ausentes ou em branco são **omitidos** do YAML — nunca emitidos como string vazia, null ou placeholder. Valores com caracteres especiais são escapados via `yaml.safe_dump` (regra já em vigor da Story 1.3 AC5).
6. **AC6 — Filename slug para DOCX.** `backend/file_writer.py::save` DEVE produzir um `.md` com nome seguindo a mesma ordem de prioridade (PRD FR7): (1) título detectado, (2) nome original do arquivo (stripado de `.docx`), (3) slug — sempre terminando em `.md` (nunca `.docx.md`). Colisões resolvem com sufixo `-2`, `-3` (regra existente de Story 1.3 AC7 — não precisa de código novo se o writer já lida com extensão via `Path.stem`; se hoje ele assume `.pdf` literal, esta AC corrige para ser extensão-agnóstico).
7. **AC7 — UI: dropzone e placeholder de path aceitam DOCX.**
   (a) `frontend/templates/index.html` — o `<input type="file">` (id `pdf-file-input`) DEVE ter `accept=".pdf,.docx,application/pdf,application/vnd.openxmlformats-officedocument.wordprocessingml.document"`. O id pode permanecer `pdf-file-input` para evitar churn do `app.js` / CSS; o label da dropzone passa de "PDF Payload" para "Document Payload" e o hint passa de "Single Document Buffer / 50 MB MAX" para "PDF or DOCX / 50 MB MAX".
   (b) O texto da dropzone `dropzone__label` passa de "Drag & drop PDF here or click to browse" para "Drag & drop PDF or DOCX here or click to browse".
   (c) O placeholder de `#path-input` passa de `C:\Users\you\Documents\paper.pdf` para `C:\Users\you\Documents\paper.pdf` **ou** `.docx` — aceitar uma variação que comunique os dois formatos, sem mudar o layout (ex: `C:\Users\you\Documents\paper.pdf (or .docx)`).
   (d) O processing-card text em `#indicator` permanece válido — não menciona PDF explicitamente; não mudar.
   (e) Nenhuma mudança em `style.css` ou em `app.js` é esperada. Se alguma classe de dropzone tiver cópia hardcoded "PDF" em `style.css` content ou em data attribute, atualizar. Caso contrário, deixar inalterado.

## Technical Notes

- **Integration Approach:** Docling's `DocumentConverter` already supports `.docx` natively via its Word backend — no pipeline registration needed beyond the existing `InputFormat.PDF` option used in `main.py::lifespan`. DOCX input uses Docling's default format handling; the `PdfPipelineOptions(do_ocr=False)` setting is PDF-scoped and does not interfere.
- **Existing Pattern Reference:** mirror the PDF branch in `extract()` and `_validate_local_path` exactly — file-like → magic-byte check → `DocumentStream(name=..., stream=io.BytesIO(data))` → single-call `_run_docling`. DOCX skips `_convert_pdf_bytes` (no chunker needed).
- **Key Constraints:**
  - DOCX has no OCR / scan concern: all text is native. `_guard_non_empty_markdown` kind-specific branches must handle a new kind gracefully — add a DOCX branch (generic message: "DOCX produced no extractable text — the file may be empty or malformed") or collapse the non-HTML branches into a single "no extractable text" message parameterised by kind. Either is acceptable; prefer the explicit branch for symmetry with the existing `url_html` vs PDF split.
  - Docling version `docling>=2.0,<3.0` (from `pyproject.toml`) is known to support DOCX — no version bump required. If dev encounters a missing backend, coordinate with @devops (not @dev) for dependency changes; do not silently upgrade.
  - The URL-PDF chunking machinery (Story 1.7) is strictly bypassed for DOCX. No new config knob, no new threshold. This is explicit in AC2.
  - Error catalog (`backend/errors.py`) — no new error codes needed; reuse `INVALID_INPUT` (magic byte / extension) and `CONVERSION_FAILED` (Docling can't parse). If `hint` strings in `ERROR_CATALOG` mention "PDF" explicitly, generalise to "PDF or DOCX".

## Risk and Compatibility Check

- **Primary Risk:** Docling's DOCX backend rejects edge-case `.docx` produced by old LibreOffice / Pages / Google Docs exports, generating `ConversionError` where a user expects success. **Mitigation:** surface the exception cleanly via existing `CONVERSION_FAILED` → HTTP 422 with a hint from the catalog; do not attempt to sniff or repair. If this turns out to be chronic in practice, a follow-up story can add a compatibility probe — out of scope here.
- **Secondary Risk:** File-writer collision handling assumed `.pdf` → `.md` in places. **Mitigation:** Task 4 audits and makes it extension-agnostic; integration test exercises `.docx` → `.md` explicitly. Rollback is trivial — the change is local to `file_writer.py`.
- **Rollback:** revert the single commit (or the merged PR). No migrations, no persistent state, no schema change. PDF/HTML paths use the same code paths plus a new branch — reverting removes the branch without touching existing logic.

**Compatibility Verification:**

- [x] No breaking changes to existing API: `/extract` JSON response shape unchanged. `SourceKind` literal gains new values but JSON serialization exposes only `kind` as string — consumers reading the string continue to work; consumers doing exhaustive match on the literal (none exist today outside the codebase) would need updating.
- [x] No database: N/A.
- [x] UI changes follow existing design patterns: same dropzone, same buttons, same result card. Text-only changes in labels.
- [x] Performance impact negligible: DOCX single-call via DocumentConverter singleton — same profile as URL-HTML conversion.
