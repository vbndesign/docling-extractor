## Story

**As** the owner of the tool,
**I want** the extraction pipeline to convert large PDFs (100+ pages) to Markdown without silently losing pages, **and** to surface any partial conversion clearly to the UI and to the output file,
**so that** I can trust that a 200 OK from `/extract` means I actually got the full document, not a 10 % fragment with the other 90 % discarded.

## Acceptance Criteria

1. **AC1 — Chunked PDF extraction.** Para qualquer fonte PDF (`pdf_upload`, `pdf_local_path`, `url_pdf`), o serviço DEVE dividir o PDF em blocos de `PDF_CHUNK_SIZE` páginas (default 10) quando o total de páginas for `> PDF_CHUNK_THRESHOLD` (default 20), converter cada bloco separadamente pelo `DocumentConverter` singleton e concatenar os markdowns resultantes na ordem original. PDFs com `pages <= PDF_CHUNK_THRESHOLD` continuam passando em chamada única (rota rápida preservada).
2. **AC2 — Sem regressão de conteúdo.** Para um PDF de referência ≥ 100 páginas com texto nativo (fixture `tests/fixtures/large_text.pdf`), a conversão via `/extract` DEVE resultar em markdown cuja contagem de caracteres significativos seja **≥ 90 % do total de caracteres extraíveis** nativamente por `pypdfium2` (medido na fixture ao longo de `get_textpage().get_text_range()` por página). O teste deve comparar contra o baseline da fixture e falhar se a razão cair abaixo de 0,90.
3. **AC3 — Status agregado dos chunks.** Quando 1+ chunks retornam Docling status `PARTIAL_SUCCESS` OU `FAILURE`, o serviço DEVE:
   (a) agregar `failed_pages` globais (números 1-based em relação ao PDF inteiro, não ao chunk);
   (b) se `len(failed_pages) / total_pages > MAX_FAILED_PAGES_RATIO` (default 0.10) OU se **zero chunks** produziram markdown — levantar `ConversionError` com mensagem "Conversion failed for N of M pages (over threshold)";
   (c) caso contrário, devolver o markdown parcial junto com um campo novo `partial` no frontmatter e os `failed_pages` explicitados no YAML.
4. **AC4 — Frontmatter para conversão parcial.** Quando AC3 (c) se aplica, o YAML gerado por `frontmatter.build` DEVE incluir as chaves `partial: true` e `failed_pages: [n, n, n]` (lista ordenada, 1-based). Quando toda a conversão for bem-sucedida, essas chaves NÃO devem aparecer (consistente com a regra "omissão > placeholder" — FR4 / arch §5.2).
5. **AC5 — Visibilidade na UI.** A resposta HTMX do caso partial DEVE exibir, no `result-card` de sucesso, um bloco adicional (style: warning / amarelo — já previsto em `frontend-spec` para avisos) listando o número de páginas falhas e os números delas (ex: "Extração parcial — 4 páginas perdidas: 13, 14, 45, 46"). JSON response deve ganhar campos `partial: bool` e `failed_pages: list[int]`.
6. **AC6 — Timeout aumentado e configurável.** `REQUEST_TIMEOUT_SECONDS` default passa de **60 s → 600 s** (10 min) para acomodar PDFs ~100 páginas (~3 min observados). O valor continua lido de env var. README atualizado. Sem nova configuração — só o default muda.
7. **AC7 — Testes automatizados.**
   (a) Unit: `_chunk_pdf_bytes(data, chunk_size)` divide corretamente um PDF de N páginas em `ceil(N/chunk_size)` blocos que, somados, voltam às N páginas originais.
   (b) Integration: endpoint `/extract` com fixture `large_text.pdf` (104 páginas) retorna 200, `partial: false`, markdown chars ≥ 90 % do baseline (AC2).
   (c) Integration: endpoint `/extract` com fixture `partial_failure.pdf` (mock via patch de `_run_docling`) que simula 1 chunk `PARTIAL_SUCCESS` com 2 páginas falhas → response tem `partial: true, failed_pages: [13, 14]`, HTML do HTMX mostra o aviso.
   (d) Integration: endpoint `/extract` com mock que falha 50% das páginas → 422 `CONVERSION_FAILED` (acima do `MAX_FAILED_PAGES_RATIO`).
   (e) Unit: PDFs pequenos (`pages <= PDF_CHUNK_THRESHOLD`) continuam passando por caminho single-call — teste verifica que `_chunk_pdf_bytes` não é invocado.
8. **AC8 — Regressão.** Todos os testes pré-existentes de Story 1.1–1.6 DEVEM continuar passando sem modificação (exceto ajuste de fixtures/mocks quando a assinatura interna mudar de forma benigna — mudanças isoladas documentadas no Change Log).
9. **AC9 — Lint e performance.** `ruff check backend tests` e `ruff format --check backend tests` passam. Suíte completa (excluindo testes `slow`) continua rodando em <60 s (AC5 da Story 1.6 preservado).

## Dev Notes

### Previous Story Insights (handoff técnico do @dev em 2026-04-19)

O autor relatou markdown com ~10 % do conteúdo de um PDF de 100 páginas e logs `std::bad_alloc` + `"Stage preprocess failed for run 2, pages [13–20]"`. @dex rodou 4 probes sobre o PDF real (104 pg, 100 % texto nativo, 156 647 chars), com os seguintes resultados finais:

| Probe | Config | Páginas OK | MD chars | Tempo |
|---|---|---|---|---|
| A | `do_ocr=False` | **segfault** | — | — |
| B | `do_ocr=False` + `do_table_structure=False` | 14/104 | 25 425 | 41 s |
| C | `do_ocr=False` + `images_scale=0.5` + `num_threads=1` | 14/104 | 25 081 | 35 s |
| **D1** | Chunks 10 páginas, novo converter/chunk | **104/104** | **145 046** | 185 s |
| **D2** | Chunks 10 páginas, converter reusado | **104/104** | 145 046 | 179 s |

**Conclusões técnicas de @dex (normativas para esta story):**

1. **O estágio `preprocess` do backend pypdfium2 acumula memória nativa por página dentro de uma única chamada `DocumentConverter.convert()`.** Nenhum knob do `PdfPipelineOptions` libera esse heap. Mexer em `do_ocr`, `do_table_structure`, `images_scale`, `accelerator_options` — **irrelevantes** para este problema. Não perder tempo aí.
2. **Chunking resolve completamente** porque cada chamada `convert()` separada começa com heap limpo do pypdfium2. D2 (converter reusado) empata com D1 (novo converter por chunk), o que **prova que o converter singleton (`app.state.converter`) pode ser preservado**. Não recriar `DocumentConverter` por chunk — não traz benefício e recarrega modelos (6 s extras).
3. **O endpoint atual aceita `PARTIAL_SUCCESS` sem inspeção** (`backend/docling_service.py:137`), o que explica por que o bug passou despercebido: 90 páginas falhando resulta em 200 OK com markdown curto.

Scripts de probe ficaram em `output/_probe.py` e `output/_probe_d.py` (throwaway, **deletar ao final da story** — Task 10 confirma isso). Markdowns de probe em `output/_probe_*.md` também são descartáveis.

### Architectural Invariants (imutáveis)

[Source: arch §2.2 R1/R2 + §10.3]

- **R1** (CPU-bound Docling): qualquer invocação de `_run_docling` continua via `asyncio.to_thread` — o loop por chunks também. **Não** transformar em subprocess-per-chunk (funcionaria mas dobra a latência recarregando modelos de ~600 MB; D2 já demonstrou que reuso in-process é seguro).
- **R2** (lifespan singleton): `app.state.converter` continua sendo instanciado uma única vez no lifespan. Chunks reutilizam.
- **§10.3 Boundary rules**: `docling_service` só levanta `DoclingExtractorError`. Falha agregada acima do threshold → `ConversionError` existente (código `CONVERSION_FAILED` já no catálogo — arch §10.2).
- **FR4 / §5.2 Frontmatter**: campos opcionais são **omitidos** quando ausentes, não setados como `null`/`[]`. Portanto `partial: false` e `failed_pages: []` **não devem aparecer** no YAML quando a conversão for 100 % limpa. No JSON da API, em contraste, os campos são sempre presentes (contratos diferentes; arch §7.2 para API, §5.2 para frontmatter).

### Chunker Reference Implementation

[Source: probes D1/D2 do @dev, validados contra o PDF real]

```python
import io
import pypdfium2 as pdfium

def _chunk_pdf_bytes(data: bytes, chunk_size: int) -> list[bytes]:
    src = pdfium.PdfDocument(io.BytesIO(data))
    try:
        n = len(src)
        out: list[bytes] = []
        for start in range(0, n, chunk_size):
            end = min(start + chunk_size, n)
            dst = pdfium.PdfDocument.new()
            try:
                dst.import_pages(src, list(range(start, end)))
                buf = io.BytesIO()
                dst.save(buf)
                out.append(buf.getvalue())
            finally:
                dst.close()
        return out
    finally:
        src.close()
```

**Notas importantes:**
- `pypdfium2` é dep transitiva do Docling desde a Story 1.1 — não precisa ser adicionada ao `pyproject.toml`.
- `PdfDocument.import_pages` aceita uma lista de índices **0-based**. Falha comum: passar índices 1-based e perder a página 0.
- `dst.close()` é necessário pra liberar o handle nativo (caso contrário o próprio chunker vai acumular memória do jeito que o Docling faz hoje).
- `io.BytesIO(data)` pro `src`: pypdfium2 aceita path-string ou file-like; já que trabalhamos em memória (upload, url_pdf), file-like é o natural.

### Page-Number Offset em Failed Pages

[Source: probes do @dev + Docling source]

Quando o Docling falha na página 3 do **chunk 2** (páginas 11–20 do PDF original), o `result.errors[i].page_no` será `3` (relativo ao chunk). O código em `extract()` deve aplicar o offset:

```python
global_failed = [offset + p for p in chunk_failed]
# onde offset = chunk_index * pdf_chunk_size
# e chunk_failed = lista 1-based de falhas locais ao chunk
```

Falhar em aplicar esse offset produz `failed_pages` incorretos (ex: "página 3 falhou" quando foi a página 13), o que destrói a utilidade do AC5.

### Partial-Success Aggregation Rule

[Source: @dex investigation + arch §10.2 `CONVERSION_FAILED`]

Decisão: o threshold `MAX_FAILED_PAGES_RATIO = 0.10` foi escolhido porque:
- Menos rigoroso (ex: 0.01) dispararia `ConversionError` em PDFs onde Docling legitimamente tropeça em 1–2 páginas com layout exótico — usuário perde o resto da conversão por nada.
- Mais tolerante (ex: 0.30) permitiria releases em que 1/3 do doc está silenciosamente faltando, mesmo com aviso — o valor semântico do "200 OK + partial" vira duvidoso.
- 0.10 cobre o intervalo prático: tolera falhas isoladas, mas rejeita o cenário do incidente (86/104 = 83 % de falhas).

Configurável via env `MAX_FAILED_PAGES_RATIO` para quem quiser ajustar.

### Completion Notes List

1. **Chunker sem regressão para PDFs pequenos.** `_chunk_pdf_bytes` NUNCA é chamado para PDFs com `pages <= pdf_chunk_threshold` (padrão 20). O `test_small_pdf_bypasses_chunking` instala um spy que falha hard se o caminho single-call acidentalmente rotear através do chunker — sem regressão silenciosa possível.
2. **Offset de página no agregador.** Docling reporta `result.errors[i].page_no` relativo ao **chunk** (1-based). `_convert_pdf_bytes` aplica `offset = chunk_index * chunk_size` antes de agregar. O teste `test_large_pdf_aggregates_failed_pages_with_chunk_offset` força o chunk 2 a reportar pages `[3, 4]` e confirma globalmente `[13, 14]`. Se alguém inverter essa aritmética, o teste falha imediatamente com a diferença entre os dois conjuntos.
3. **Threshold enforcement.** Quando `failed_pages / total_pages > max_failed_pages_ratio`, `_convert_pdf_bytes` levanta `ConversionError("Conversion failed for N of M pages (over threshold X).")`. O mapper de erros existente (arch §10.2) traduz isso para **HTTP 422 `CONVERSION_FAILED`** sem que `extract()` precise customizar o tratamento.
4. **Frontmatter FR4-compliant.** `frontmatter.build` só emite `partial:` + `failed_pages:` quando `partial=True` (via novo kw-arg `partial_info=(bool, Iterable[int])`, default `(False, ())`). Em conversões limpas, o YAML fica idêntico à Story 1.6 — o teste `test_build_defaults_match_clean_conversion` garante BC byte-a-byte.
5. **JSON API vs. Frontmatter (contratos diferentes).** A resposta JSON SEMPRE inclui `partial` + `failed_pages` + `total_pages` (mesmo em sucesso limpo, shape estável para scripts). O `.md` no disco só inclui quando há partial. Isso é documentado inline em `backend/main.py::extract_endpoint` e coberto pelo teste `test_extract_success_emits_partial_false_in_json_response`.
6. **Warning block UI — deviation minimal do design system.** O frontend-spec v1.1 **não** catalogou tom de aviso/amber apesar do que a story assume. Para respeitar "não criar token novo" e mantendo o aviso visualmente distinto de erro (vermelho) e sucesso (verde), `.partial-notice` usa `--color-accent` (azul) como barra lateral — semanticamente "informação / atenção". Pequena adição de CSS (só existentes tokens reutilizados), documentada inline e justificada. Alternativa seria reusar `.error-message` (vermelho) mas seria confuso UX-wise para um caminho que retorna 200 OK com arquivo salvo.
